# Universal climbing performance evidence

`WorldProfile.Run` sampled the same seed-2409 Downtown dense street at 1280×720, Ultra quality, with 29 NPCs and one batch Editor process. The hero was active but idle except in the explicitly labeled hero-inactive diagnostic. Each run used three unprofiled four-second rounds and a separate profiled round. The city object counts, camera position and hardware matched. These are Editor throughput measurements, not standalone-player FPS.

The first after median is 29.85% lower FPS and 5.18 ms higher frame time than before. The unchanged-code repeat is 32.64% lower FPS and 5.90 ms higher frame time. Both observed slow runs remain in the record. The later hero-inactive diagnostic reached a 73.11 FPS median, but it changes the active-hero condition. An immediately adjacent active-hero run with unchanged source reached a 76.74 FPS median, 6.53% below and 0.85 ms above the before median. It measured `Update.ScriptRunBehaviourUpdate` at 0.664 ms versus 0.668 ms before, `PlayerLoop` at 12.140 versus 11.562 ms, and `PostLateUpdate.BatchModeUpdate` at 6.488 versus 5.949 ms. The large slowdown therefore did not repeat consistently under the same code and active-hero condition. The profiled street markers in the first slow after run were `PlayerLoop` 17.210 ms, `Update.ScriptRunBehaviourUpdate` 0.946 ms, `PostLateUpdate.BatchModeUpdate` 8.539 ms, render opaque geometry 2.544 ms and skinned-mesh update 1.338 ms; before they were 11.562, 0.668, 5.949, 1.605 and 0.819 ms respectively. City generation/NavMesh stages also took longer. Host load differed across runs, so attributing the gap to Editor/host variability is an inference, not a proven cause. Performance acceptance remains **inconclusive**, not a pass. All active-hero samples are idle and do not execute `TryClimb` without movement input.

In the final dedicated fixture, a no-wall `TryClimb` probe averaged **0.001031 ms/call over 10,000 calls** and allocated **0 managed bytes in 1,000 calls** (`Verification/Climbing/probe-cost-final`). The sample establishes low isolated query cost on this machine; it does not establish active-climbing frame throughput or prove that other gameplay code allocates nothing. All four after profiles exited 0; the real progression save and Sidekick database SHA-256 values remained `eec464258211eb2e09498061618cf57b67f63c57f77f20015e92990e616ce899` and `21f8687dd60dcee4fdc871e5c351d8267f160fcd4e6bd6a8ceabf236df15866b`.

A subsequent `ClimbingVerification.City` run at the generated seed-2409 Downtown tower sampled 1.2 seconds each of attached idle, ascending, and attached idle again in the same Editor process. It passed **29/0**, exit 0. The three wall-clock samples were **131.16 / 133.06 / 139.14 FPS**, **7.624 / 7.515 / 7.187 ms/frame**, and **1502 / 1397 / 1390 whole-frame GC B/frame**. The ascending segment rose **6.667 m** and remained attached; both idle segments had zero rise. Thus active climbing was within the bracketing idle throughput in this fixture. This is a local paired diagnostic, not a matched dense-street before/after or standalone-player performance sign-off. Camera height changes during ascent, and `Time.captureDeltaTime` is fixed at 1/120 for deterministic movement verification. The full output and unchanged real-save/database hashes are in `Verification/Climbing/active-city-throughput/`.
